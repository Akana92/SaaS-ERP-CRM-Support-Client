# Скорость локального демо: 19 сентября 2026

Проверка после сообщения пользователя «игру отключил». Исходный сервер фактически был выключен, хотя старый `server.json` содержал `running`; HTTP не отвечал, GPU был свободен. Старый снимок статуса не использовался как доказательство работающего процесса.

## Решение

В запуске live-демо включён существующий `sdpa_repeat_kv`: он разворачивает группы K/V и использует эффективное CUDA-ядро внимания. Веса F, основная модель BF16, адаптер FP32, prompt, история, лимит ответа, sampling и граф не менялись. Base по-прежнему отключает адаптер. Загрузка без live-настройки сохраняет исходный SDPA; обучение и замороженная оценка не переключаются.

Обратимый выбор запуска: `scripts/live_demo.py start --attention sdpa_repeat_kv` (новое значение по умолчанию) или `--attention sdpa` (исходный путь). Сначала остановить работающий сервер штатной командой `stop` и дождаться `stopped`; одновременно два GPU-сервера не запускать. Настройка записывается в launch/server JSON и runtime `serving_optimizations`.

## Измерения

Артефакты: `artifacts/stage5/latency-2026-09-19/`. Скрипт `scripts/profile_live_inference.py` читает только учебную политику и демо-ERP. Единственный авторский вопрос: «Проверьте счёт INV-1002: прошла ли оплата?». Это диагностика serving, не оценка качества модели; защищённые вопросы и эталоны не читались.

Устройство RTX 3080 Laptop 16 GB; torch 2.6.0+cu124, Transformers 4.57.6, PEFT 0.19.1. На входе 4559 токенов, на выходе Base 145 / F 162. KV-cache включён; после первого forward остальные получают по одному токену. Модели измерялись последовательно, без параллельной игры. CUDA events охватывают каждый forward, синхронизация только после генерации. Это интервалы исполнения с возможными промежутками dispatch, не сумма чистого времени GPU-ядер.

Переход внимания уменьшил пик allocated примерно с **14,3 до 8,9 GiB**. Эффект для F по общему времени умеренный: основная задержка остаётся в последовательной генерации и LoRA. Один CPU-поток не принят. Проба BF16 адаптера показала дополнительное ускорение, но **не включена в сервис**: проверен лишь один вопрос, более широкая проверка этого изменения численной точности не выполнена.

Старые 99,785/334,082 секунды Base/F от 17 сентября измерялись при другой нагрузке. Нельзя приписать всю разницу одному изменению кода или считать её доказанным эффектом закрытия игры. Корректное сравнение оптимизации — текущий SDPA против текущего эффективного внимания.

## Проверка ответов и ограничения доказательств

У F на данном вопросе совпали категория, приоритет, настроение, действие, решение о передаче и evidence IDs. Изменился порядок слов в первой фразе: обе версии сообщают, что в учебной ERP оплата не зарегистрирована, не отрицают возможное списание в банке и не предлагают повторную оплату. Base сохранила точный raw-ответ при сравнении `threads1` / `efficient`. Это локальная проверка регрессии, не новая метрика качества и не обещание одинаковых ответов на всех входах.

В первом запуске `baseline` обнаружена ошибка только в диагностическом хеше: скрипт обращался к `raw_text` вместо `raw_response` и хешировал `None`. Исходные файлы сохранены. Эти хеши непригодны для проверки равенства; времена, token counts и сохранённые parsed results пригодны. Следующие запуски исправлены, сохраняют raw response и проверяют число forwards, длины входа, complete usage и валидность результата.

Замеры profiler включают накладные расходы hooks. Итоговый HTTP-прогон обычного сервера сохраняется отдельно в `http/http-smoke.json`; он проверяет реальные запросы, историю и сравнение без hooks. Он не заменяет нагрузочное испытание множества пользователей или максимальной длины диалога.

## Техническое обоснование

В установленном wheel `torch.backends.cuda.is_flash_attention_available()` возвращает false. HF 4.57.6 включает native GQA для torch ≥2.5 без маски; PyTorch 2.6 документирует GQA для Flash/math, но не efficient. Уже существующий проектный helper повторяет K/V до одинакового числа heads и явно выбирает efficient без молчаливого перехода на math. GPU-прогон этого пути завершился успешно. Никаких обновлений библиотек или новых зависимостей не потребовалось.

- [PyTorch 2.6: SDPA и ограничения GQA](https://docs.pytorch.org/docs/2.6/generated/torch.nn.functional.scaled_dot_product_attention.html).
- [Transformers: выбор GQA](https://github.com/huggingface/transformers/blob/753d61104116eefc8ffc977327b441ee0c8d599f/src/transformers/integrations/sdpa_attention.py#L29-L73).
- [PyTorch 2.6: проверка доступности backend](https://docs.pytorch.org/docs/2.6/backends.html#torch.backends.cuda.can_use_efficient_attention).

В stderr старого и нового серверов присутствует одинаковое предупреждение `UnicodeDecodeError` в reader-потоке subprocess при запуске. Оно предшествует успешному запуску HTTP. Вызывающий сторонний компонент по стеку не установлен; это известный диагностический пробел, не основание менять зависимости или скрывать сообщение.

Результат F 49/100 / Base 10/100 остаётся прежней AI-assessed NF4 оценкой QUALIFIED, не human review и не оценкой этого BF16 live-прогона. Обучение, пересудейство и итоговый test не запускались.
